## 1. The question — stated precisely
Not "does this sync?" but: **"Does this engine sync correctly on a physical iPhone, a physical mid-range Android, AND React Native Web in real browsers — today, in its current (for PowerSync, BETA) state, against our actual consolidated baseline schema and RLS?"**

Simulators do not count (hardening S2): they don't surface memory pressure, thermal throttling, real keyboards, OPFS quota, or storage eviction. The G0 exit criterion is **evidence on three physical targets.**

## 3. Test matrix — 2 candidates × 3 runtimes × scenarios
Each cell is PASS / PASS-WITH-CAVEAT / FAIL, with captured evidence (logs, DB state, screen recording).

### 3.1 Baseline capability (all runtimes)
| ID | Scenario | Pass criterion |
|---|---|---|
| B1 | Initial hydration of a typical scope (1 org, ≤25 projects, ≤2000 tasks) | Completes with progress; ≤60 s on 4G (the hydration budget from the sync design doc, §14-A — validate it here against real row counts) |
| B2 | Online create/update/delete round-trips to server and back to a 2nd client | Converges; RLS-scoped (only visible rows) |
| B3 | **Tombstone / delete-while-offline** — client A offline, row deleted on server, A reconnects | A learns the delete (does not resurrect it). This is the offline-native schema's whole point |
| B4 | Cursor correctness `(updated_at, id)` under paging | No row skipped or duplicated across page boundaries |
| B5 | Schema shape fit — the engine handles our real tables, FKs, RLS | No table/relationship the engine cannot express |

### 3.2 Offline write path (all runtimes)
| ID | Scenario | Pass criterion |
|---|---|---|
| W1 | Offline create task → reconnect | Replays; idempotent (client UUID); one row |
| W2 | Ordered, dependency-aware replay — photo on an offline-created task | Photo replays AFTER its task |
| W3 | Reference offline day: 8 h, 40 photos, 12 check-ins, 30 mutations, no signal → reconnect | Outbox drains to empty within 5 min (E4 AC②) |
| W4 | Conflict — two clients edit the same task | Deterministic resolution matching our per-entity policy (LWW-with-server-guard) |

### 3.3 NATIVE-specific (iOS + Android)
| ID | Scenario | Pass criterion |
|---|---|---|
| N1 | Kill app mid-upload → relaunch | Outbox survives; reconcile-on-launch resumes (Expo background upload survives suspension, NOT termination — known trap) |
| N2 | Reboot device with full outbox | No loss |
| N3 | Encryption at rest (SQLCipher) coexists with the engine's local DB | Engine works with an encrypted store, or documents the gap |
| N4 | Secure-store session (expo-secure-store 2048-byte cap → chunking) | Engine auth token storage doesn't break on large Supabase sessions |

### 3.4 WEB / RNW-specific — the hardest arm (this is what the spike exists to settle)
| ID | Scenario | Pass criterion |
|---|---|---|
| R1 | **PowerSync RNW beta setup**: copy worker assets, Metro platform-specific resolution, per-platform package alternatives | Builds and runs in RNW at all — the primary unknown |
| R2 | wasm SQLite over **OPFS** basic operation | Reads/writes persist across reload |
| R3 | **Storage eviction mid-outbox** (simulate/force OPFS eviction) | No silent loss; surfaced honestly |
| R4 | **Quota exceeded** (Chrome incognito ~100 MB cap) | Graceful; media retained locally; user informed (S-10) |
| R5 | **Safari private browsing — no OPFS** | App runs in **Online-only** tier and **REFUSES** to queue (never lies about state — P3). Not a crash |
| R6 | **Multi-tab, one DB** — two tabs mutating one record | Web Locks single-writer election; other tabs read through leader; no corruption (S-14) |
| R7 | Tab closed mid-upload | Background Sync is Chromium-only; on close, resumes on return (documented degradation, not loss) |
| R8 | `navigator.storage.persist()` request + tier detection at startup | Correct tier (Full / Session-durable / Online-only) reported to Sync Centre (S-13) |

## 4. Scoring rubric → the signed decision
Score each candidate. **Weighted, with hard gates.**

### 4.1 Hard gates (a FAIL here eliminates the candidate outright)
- **G-a:** B1–B5 pass on **all three** runtimes (basic sync + tombstones + cursor + schema fit).
- **G-b:** W1–W3 pass on **native** (the guaranteed-offline platforms).
- **G-c:** R5 handled correctly (Online-only refusal) — an engine that silently loses data in private browsing is disqualified.

### 4.2 Weighted score (of candidates passing all hard gates)
| Dimension | Weight | What it measures |
|---|---:|---|
| RNW maturity (R1, R2, R6, R8) | 30% | Does the web arm actually work, or is beta too raw? |
| Offline-write correctness (W1–W4, N1–N2) | 25% | The core thesis |
| Web resilience (R3, R4, R7) | 15% | Eviction / quota / tab-close behaviour |
| Schema + RLS fit (B5) | 10% | Works with our real backend, not a toy |
| Integration cost (setup friction, Metro/worker config, docs) | 10% | Dev-days to production |
| AR-05 compatibility | 10% | Can it sit behind our repository contract so no screen imports its types? "Swap in a week" must stay true |

### 4.3 Decision outcomes
1. **Both pass gates → BUY the higher-weighted.** Sign D-11 = that engine. (Recommendation expects PowerSync or ElectricSQL wins.)
2. **One passes gates → BUY it.** Sign D-11.
3. **Both pass native but FAIL RNW hard gates → BUY for native, web launches Online-only at G6.** Sign D-11 = buy-for-native + record the blow-up-scenario contingency (web loses field-offline value; native carries full offline). **ESCALATE per kickoff.**
4. **Both fail even native → BUILD bespoke** (100–160 dev-days; the schedule stretches P3a to ~6 weeks). Sign D-11 = build. **ESCALATE.**

### 4.4 Escalation triggers (kickoff `escalate_immediately_if`)
- **PowerSync AND ElectricSQL both unusable on React Native Web** → outcome 3, escalate to Moh at decision time.
- Anything that would require breaking a guardrail to hit a date.
